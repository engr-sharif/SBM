Every number quoted below is also emitted, on each run, into the machine-generated

diff there rather than as stale prose here.  `tools/build_cad_native.py` carries

## What was searched, and what was found

EA's Civil 3D surfaces live in `AECC_TIN_SURFACE` objects that libredwg cannot
decode.  It derails on one object per file and emits the remaining ~183.6 MB of
the `AcDbObjects` section as a single undecoded blob, so the surfaces are in
there as raw bytes.  Three routes were tried.

**(a) Proxy graphics — dead, definitively.** Every `AECC_*` object in C-BASE,
01.01, 02.01 and 02.02 carries a `preview` blob and every one of them is
676–688 bytes: an `AcDbProxyEntity` header plus the UTF-16 class name
(`AeccDbSurfaceTin (AeccLand1300)`).  No AcGi world-draw segments at all — EA
saved with `PROXYGRAPHICS` off.

**(b) Raw byte scan — works, and is how the existing surfaces were recovered.**
Civil 3D stores surface points as **stride-4 little-endian float64 records
(x, y, z, id64)** beginning at an arbitrary **bit** offset inside the object
stream.  Earlier attempts failed because they swept bit-shifts *or* byte
offsets but never the product of the two; the arrays in this project sit at
**bit = 1, byte = 4**.  The scanner sweeps all 64 (bit, byte) combinations over
every byte of the blob and over every decoded object's `unknown_bits`, then
segments the hits into contiguous stride-4 runs so that distinct surfaces come
out as distinct runs.

| file | blob | large runs found |
|---|---|---|
| `1578546 - C-BASE.dwg` | 183,607,533 B | 1 — 955,387 pts |
| `1578546 - 01.01 - SiteExcavAndCapping.dwg` | 183,607,536 B | 1 — 955,387 pts |
| `1578546 - 02.01 - SiteRepository.dwg` | 183,607,588 B | 1 — 955,387 pts |
| `1578546 - 02.02 - North_lobe.dwg` | 183,607,536 B | 1 — 955,387 pts |
| `1578546 - 02.03 - Borrow_Area_193e7.mms` | 272,737,606 B inflated | 1 — 933,112 pts |

The 955,387-point array is **byte-identical between 01.01 and 02.02** (verified
directly): the sheets xref C-BASE and bind the same existing surface, which is
itself a cross-check on the decode.  The `.mms` is a ZIP whose single member is
one DEFLATE stream carrying the same record layout.

**(c) There is no proposed-grade TIN in the delivered files.**  This is a
result, not an unfinished search.  Outside the one 955 k-point existing TIN the
only stride-4 runs anywhere are six small sets of dense 3-D linework, and every
one of them sits on existing ground:

|---|---|---|---|---|---|
| 02.01 | 312 | 6373872–6374282 | 2128482–2128859 | 1403.4–1441.0 | median +0.14, 55 % within 0.3 ft |
| 02.01 | 461 | 6373758–6374297 | 2128508–2128905 | 1401.7–1441.0 | median +0.03, 76 % within 0.3 ft |
| 01.01 | 235 | 6370348–6370631 | 2129381–2129657 | 1339.0–1348.6 | mean +0.05, sd 1.25, 90 % within 0.3 ft |
| 01.01 | 269 | 6370979–6371294 | 2129612–2129920 | 1349.2–1358.4 | mean +0.18, sd 1.72, 91 % within 0.3 ft |
| 01.01 | 283 | 6370985–6371288 | 2129605–2129919 | 1350.3–1359.3 | mean +0.14, sd 1.66, 94 % within 0.3 ft |
| 02.02 | 419 | 6371047–6371413 | 2129948–2130373 | 1329.0–1336.8 | mean −0.38, sd 1.58, 70 % within 0.3 ft |

The two 02.01 sets looked like the repository final grade — a flat 1441.0 ft top
and points up to +50 ft over lidar — and they are not.  The lidar *under* the
z = 1441.0 cluster is 1441.0 ft (mean of the cluster 1438–1440); the +50 ft
outliers are contour-label leader endpoints; and clipping the Delaunay to
triangles with a real edge length collapses the coverage from the 410 × 380 ft
bounding box to 0.2 acres with a maximum of +12 ft.  Point spacing is 0.4–2.6 ft
along lines.  They are existing contours drawn densely, not a surface.

`repo_fg` and `nlobe_fg` are therefore recorded in `surfaces.json` under
`not_recovered` rather than shipped.  **The spec's constrained-Delaunay fallback
was deliberately not used**, because its input is not present: the `grade` group
is 47 features totalling 145 vertices — mostly 2-point contour stubs spanning a
40 ft strip of the East Stockpile — and the `daylight` group carries a usable Z
on 17 of its 187 vertices.  A triangulation over that would invent the entire
pad, which is the failure CLAUDE.md warns against ("do not synthesise a surface
from the breaklines and call it the design").  **The remedy is one line to EA:
ask for a LandXML export or a proposed-grade raster of the repository and north
lobe surfaces** — something they can produce from Civil 3D in a minute.

## Rasterisation

All four surfaces are terrain-RGB PNGs at 1 ft in the app's standard encoding
(`v = R*256 + G`, `z = zmin + (v−1)*zstep`, `v = 0` nodata, PNG row 0 north) —
the same convention `tools/build_dems_from_master.py` writes and `js/dem.js` and
`js/cadnative.js` read.

The recovered TINs are rasterised by **linear interpolation over their own
Delaunay triangulation**, with triangles longer than 25 ft (≈ 7× the 3.7 ft
point spacing) dropped so the interpolation cannot bridge the concave parts of
the hull.  Nearest-cell binning was tried first and is wrong for these surfaces:
at 3.7 ft point spacing a 1 ft grid built by binning is **84 % nodata**, so
`surfaceElev` returned NaN across most of the residential lots — a raster that
looks like a surface and behaves like confetti.  Interpolation takes `eg_ea` to
61.9 % of its window filled (the rest is genuinely outside the TIN) and makes
the PNG *smaller*, because interpolated terrain compresses and speckle does not.

### Depth overrides that are NOT applied

Depth is taken exactly as `tools/build_cad_native.py` left it — every closed
excavation polygon carries `depth_ft = 1.0` from the sheet note "EXCAVATE WORK
AREA TO ONE FOOT DEPTH UNLESS OTHERWISE INDICATED".  The 6-inch call-outs it
found are sheet-level leader annotations naming a *spot*, not a closed region,
so none of them is attached to a polygon.  They are carried into `surfaces.json`
as `depth_overrides_unapplied` so the 0.5 ft areas stay visible instead of
silently becoming 1.0 ft:

| sheet | depth ft | call-out |
|---|---|---|
| C-104 | 0.5 | "EXCAVATE AND BACKFILL AS PER SPECIFICATIONS, EXCEPT TOP 6" SHALL BE SAME SOIL AS ON FOOT PATH." |
| C-107 | 0.5 | "6" EXCAVATION BY HAND WITHIN DRIP LINE. TREE ROOTS SHALL NOT BE DAMAGED…" |
| C-111 | 0.5 | "FILL 6" NEAR STRUCTURE" |
| C-111 | 0.5 | "FILL 6" CLEAN SOIL ALONG FENCE LINE AND MATCH TREE DRIP LINE FILL…" |

Closing them needs a region, not a leader: either EA's hatch boundaries for the
dripline/structure zones, or a decision to buffer the call-out leader tip.  Both
are judgement calls that belong to the design lead, so the surface uses 1.0 ft
throughout and the exceptions travel with the data.

## Extent of the residential rasters

§5 asks for existing ground "elsewhere inside bbox"; the raster instruction asks
for "the footprint bbox with nodata outside".  Both are honoured by carrying
existing ground out to a **60 ft working buffer** around the excavation limits
and leaving the rest of the bbox nodata.  Any volume polygon, section or isopach
drawn around a lot still lands on a continuous surface, while the ~89 % of this
tall thin bbox (1426 × 4199 ft) that is nowhere near an excavation stops paying
payload for a second copy of a DEM the app already ships as `dem_abp` /
`dem_site`.  It takes the two residential rasters from 4.5 MB to 1.1 MB with no
analytical loss.

## App API

`SBMM.CadNative` exposes `{groups, layers, features, byHandle, sheet_notes,
surfaces, notRecovered}` plus:

```
SBMM.CadNative.surfaceElev(id, x, y)   // ft, NaN outside / nodata / not yet decoded
SBMM.CadNative.surfaceReady(id)        // Promise, resolves once decoded
SBMM.CadNative.surfaceMeta(id)         // the manifest entry
SBMM.CadNative.loadSurface(id)         // force the decode
```

Decoding is lazy and happens at most once per surface: the rasters are ~8.5 MB
of PNG between them and nothing pays for that until something asks for an
elevation.  Because `createImageBitmap` is async and `surfaceElev` is not, **the
first call for a surface kicks the decode off and returns NaN** — await
`surfaceReady(id)` when the numbers have to be there on the first try.  Lookup
is nearest-cell on the 1 ft grid: the rasters *are* the design at 1 ft, so
interpolating between cells would invent precision the source does not have.

## Reproducing

```
python3 tools/build_cad_surfaces.py \
    --master /path/master_1ft.f32 \
    --tin    /path/exc_tin_ordered.npy \
    --borrow /path/borrow_pts_sp.npy \
    --cad    data/design/cad_native.json \
    --gis    data/design_gis.json \
    --out    data/design --datajs datajs
```

`--tin` / `--borrow` are the recovered point arrays.  The whole chain that
produces them is in the repo:

```
dwgread -O JSON -o dump.json "1578546 - 01.01 - SiteExcavAndCapping.dwg"
python3 tools/pull_dwg_blob.py     dump.json blob.bin   # the one giant object
python3 tools/scan_dwg_surfaces.py blob.bin  exc        # sweep the blob
python3 tools/scan_dwg_objects.py  dump.json excobj     # sweep decoded objects
```

`scan_dwg_surfaces.py` writes `TAG_runs.npy` with columns
`x, y, z, id64, run_index`; the run holding the surface is the `--tin` input.
Converting the DWGs needs **libredwg git master** (`dwgread` 0.14.x); release
0.13.3 cannot decode these Civil 3D files.
